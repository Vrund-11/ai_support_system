# Architectural Decision Records (ADRs) - SupportPilot

## ADR-001: Migration from IVFFlat to HNSW Vector Indexing in PostgreSQL pgvector

### Status

Accepted

### Context

SupportPilot uses PostgreSQL with the `pgvector` extension for semantic vector search over knowledge base article chunks (`kb_chunks`).
Previously, the schema utilized an IVFFlat index (`idx_kb_chunks_embedding ON kb_chunks USING ivfflat (embedding vector_cosine_ops) WITH (lists = 100)`).

IVFFlat operates by partitioning vectors into Voronoi cells via k-means clustering. This approach suffers from notable drawbacks:

1. **Index Build Timing & Cluster Balancing**: IVFFlat requires existing training data at index creation time to build balanced clusters. For small or moderately-sized tenant knowledge bases (< 100k chunks) or dynamically growing corpora, IVFFlat produces unbalanced centroids and severely degraded recall unless rebuilt frequently.
2. **Hyperparameter Tuning**: Finding the optimal number of `lists` (probes) requires manual tuning based on dataset size, and query-time `ivfflat.probes` must be scaled up to achieve acceptable recall, significantly degrading latency.
3. **Recall vs Latency**: IVFFlat recall drops substantially on multi-topic and technical corpora compared to graph-based indexes.

### Decision

Migrate the vector index on `kb_chunks.embedding` to **Hierarchical Navigable Small World (HNSW)**:

```sql
DROP INDEX IF EXISTS idx_kb_chunks_embedding;
CREATE INDEX IF NOT EXISTS idx_kb_chunks_embedding
    ON kb_chunks USING hnsw (embedding vector_cosine_ops)
    WITH (m = 16, ef_construction = 64);
```

At query execution time, the session sets:

```sql
SET hnsw.ef_search = 40;
```

In addition, `kb_chunks.metadata` tracks `embedding_model` (`sentence-transformers/all-MiniLM-L6-v2`) to ensure queries only compare vectors generated by the same model architecture and dimension (384).

### Rationale & Parameters

- **`m = 16`**: Maximum number of bidirectional connections per element in the HNSW graph. 16 balances graph memory footprint and navigation recall across multi-dimensional embeddings (384 dimensions).
- **`ef_construction = 64`**: Size of dynamic candidate list during graph construction. 64 ensures high quality link selection during incremental chunk ingestion without excessive indexing latency.
- **`ef_search = 40`**: Size of dynamic candidate list during nearest-neighbor query traversal. 40 yields >98% recall on cosine distance while maintaining sub-5ms query latency.
- **Dynamic Updates**: Unlike IVFFlat, HNSW supports incremental insertions without index rebuilding and maintains high recall even with sparse initial datasets.

### Consequences

- **Positive**: High recall immediately upon first document ingestion; zero need for retraining clusters; deterministic nearest-neighbor retrieval.
- **Trade-off**: HNSW consumes more RAM and build time than IVFFlat; mitigated by SupportPilot's chunk size (~500 tokens) and bounded corpus per tenant.

## ADR-002: TanStack Query Optimistic Updates & ClientID Deduplication

### Status

Accepted

### Context

In real-time support interactions, network roundtrips (HTTP POST -> gateway -> ticket-service -> MongoDB -> gateway -> response) introduce visible UI latency (150ms - 300ms) when agents submit replies or internal notes. Furthermore, because both HTTP POST responses and WebSocket broadcast events (`message:received`) deliver the newly created message to the client, dual delivery creates UI message duplication and flickering if not deduplicated.

### Decision

Implement TanStack Query cache-driven optimistic updates with temporary client-generated IDs (`clientId`):

1. **Optimistic Mutation**:
   - Agent submits reply: client generates a unique ephemeral ID `temp-${uuid}` and immediately inserts the message into TanStack Query's cache (`queryClient.setQueryData(['ticket-messages', ticketId])`).
   - The UI renders the message instantaneously with an "Optimistic" indicator badge.
2. **ClientID Tracking**:
   - The outgoing HTTP POST body includes `clientId: string`.
   - The ticket-service records `clientId` in message documents and echoes it back in HTTP responses and WebSocket events.
3. **Reconciliation & Deduplication**:
   - Upon receiving the server response or Socket.IO `message:received` event, `reconcileOptimisticMessage` searches the local cache for matching `clientId` or temporary ID.
   - It replaces the optimistic placeholder with the authoritative server record (`id`, `seq`, `createdAt`) without altering list ordering or causing re-renders.
   - If the HTTP request fails, TanStack Query `onError` rolls back the optimistic update and presents a retry action to the agent.

### Consequences

- **Positive**: Zero perceived latency on message submission (< 16ms UI update); completely prevents dual-message rendering on WebSocket reconnection; resilient offline handling.
- **Trade-off**: Slightly increased client-side state logic in `apps/web/src/lib/optimistic.ts` and component test requirements.

## ADR-003: Enterprise Secrets Management, GitLeaks Zero-Trust & Rotation Architecture

### Status

Accepted

### Context

SupportPilot handles sensitive multi-tenant credentials: JWT access and refresh signing secrets, MongoDB URIs, Redis passwords, MinIO S3 keys, and webhook HMAC keys. Embedding hardcoded secrets or committing `.env` files into source control creates critical vulnerability vectors and violates compliance policies.

### Decision

Establish a zero-trust secrets architecture enforced at build, runtime, and CI/CD stages:

1. **Automated Secret Scanning**:
   - Integrate `gitleaks` into pre-commit hooks and GitHub Actions (`.github/workflows/ci.yml`).
   - Run `gitleaks detect --redact` on every PR; block any commit containing entropy matches, private keys, or API tokens.
2. **Environment Sanitization**:
   - Strictly gitignore `.env` and `.env.local`. Maintain only `.env.example` in version control containing variable names and descriptive placeholder comments.
3. **Runtime Validation**:
   - All services parse and validate environment variables at boot using Zod (`packages/validators/src/env.ts`) or Pydantic. Any missing required secret triggers immediate process termination (`process.exit(1)`) before binding network ports.
4. **Automated Credential Rotation**:
   - Document and verify zero-downtime credential rotation procedures (`evidence/security/rotation.md`) for Redis AUTH, JWT signing secrets (supporting dual-key verification grace periods), and MongoDB user credentials.

### Consequences

- **Positive**: Zero secret leakage into git history; early failure during startup if configuration is invalid; defensible security posture during audits.
- **Trade-off**: Developers must copy `.env.example` to `.env` during initial repository setup.

## ADR-004: SQS / Lambda Transport Choice for Outbound Webhooks

### Status

Accepted

### Context

When ticket lifecycle events occur (e.g. `ticket.created`, `ticket.resolved`), SupportPilot dispatches signed HTTP POST payloads to external endpoints configured by tenants. External endpoints may be slow, rate-limited, or temporarily offline. Dispatching HTTP calls synchronously from within `ticket-service` or the main API gateway would block Node.js event loops, exhaust connection pools, and violate tenant isolation.

### Decision

Decouple webhook dispatching using AWS SQS and Lambda (emulated locally via LocalStack and SAM Local):

1. **Decoupled Architecture**:
   - `notification-service` or `ticket-service` produces a lightweight webhook event message and enqueues it into an Amazon SQS FIFO queue (`supportpilot-webhooks.fifo`).
   - The SQS queue enforces message deduplication (`MessageDeduplicationId`) and per-tenant ordering (`MessageGroupId: tenantId`).
2. **Serverless Dispatcher**:
   - AWS Lambda (`webhook-dispatcher`) acts as the event consumer. It fetches batches of events, computes HMAC-SHA256 signatures (`x-supportpilot-signature`), and executes outbound HTTP requests with configurable timeouts.
3. **Failure Isolation & DLQ**:
   - Temporary network failures trigger exponential backoff managed by SQS redrive policies (`maxReceiveCount = 5`).
   - Poison messages or permanently failing customer endpoints are routed to `supportpilot-webhooks-dlq.fifo` without impacting platform availability or other tenants.
4. **IaC Definition**:
   - All infrastructure is defined in Terraform (`infra/terraform/sqs.tf`, `infra/terraform/lambda.tf`) with parameterized endpoint URLs allowing seamless execution against LocalStack locally or real AWS in production.

### Consequences

- **Positive**: Complete fault isolation; customer webhook outages do not degrade core ticketing throughput; built-in dead-letter queuing and replay.
- **Trade-off**: Requires AWS SDK v3 dependencies and local emulation tooling (SAM Local / LocalStack).

## ADR-005: Kubernetes Kind for Local Multi-Service Cluster Validation

### Status

Accepted

### Context

SupportPilot consists of 4 backend microservices, 2 web applications, 5 datastores, Prometheus, and Grafana. While Docker Compose is convenient for developer iteration, it does not validate Kubernetes-specific constructs such as Ingress controllers, Ingress path routing, NetworkPolicies, Horizontal Pod Autoscalers (HPA), readiness/liveness probes, and rolling update strategies.

### Decision

Adopt **Kind (Kubernetes in Docker)** as the official local Kubernetes emulation and staging validation environment:

1. **Local Multi-Node Emulation**:
   - Define cluster layout in `infra/k8s/kind-config.yaml` with port mappings for HTTP (`80`) and HTTPS (`443`).
2. **Ingress NGINX**:
   - Deploy standard Ingress-NGINX controller inside Kind, mirroring production cloud ingress configurations.
3. **Kustomize Declarative Overlays**:
   - Structure manifests into `infra/k8s/base` (common deployments, services, HPAs, NetworkPolicies) and overlays (`overlays/local`, `overlays/staging`).
4. **CI Rollout Verification**:
   - In GitHub Actions (`.github/workflows/deploy-staging.yml`), build local container images, load them directly into Kind via `kind load docker-image`, apply manifests, and wait for rollouts using `kubectl rollout status`.

### Consequences

- **Positive**: Zero cloud hosting costs; identical manifest syntax between local testing and cloud production; catches pod startup timing issues and network policy restrictions before merging to main.
- **Trade-off**: Requires running Docker daemon on host or CI runner to execute Kind cluster creation.
